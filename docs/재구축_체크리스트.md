## 8. 실전 재구축 절차 요약 — 배포팀 10줄 + hailcast-rds-secret 자동화 갱신

destroy 이후 Terraform으로 다시 세운 리소스는 이름은 같아도 ARN 등 내부 ID가 새로 발급된다. 매니페스트에 그 ID를 문자 그대로 박아둔 곳만 아래 8-1의 새 값으로 바꾸면 된다. 이름으로 정해지는 값(IRSA ARN·SQS URL·ECR 주소 등)은 재구축해도 그대로다.

### 8-1. 재구축 시 고쳐야 하는 배포팀 10줄 (인프라가 값을 전달)

| 값 | 받는 곳(manifests) | 안 고치면 |
| --- | --- | --- |
| ACM 인증서 ARN (`alb_certificate_arn`) | `apps/call-api/ingress.yaml:19` · `apps/frontend/ingress.yaml:15` · `apps/predict/ingress.yaml:11` | 없는 인증서 지목 → HTTPS 리스너 안 붙음 |
| VPC ID (`vpc_id`) | `addons/aws-load-balancer-controller/values.yaml:3`의 `vpcId` | 컨트롤러가 없는 VPC 지목 → ALB 자체가 안 생김 |
| RDS 마스터 시크릿 ARN (`rds_master_secret_arn`) | `platform/external-secrets/externalsecret-rds-credentials.yaml:19,23` | ESO가 없는 시크릿 조회 → 계속 실패(단, Merge 정책이라 파드 자체는 뜸 — 로테이션만 안 반영) |
| S3 버킷 이름 (`model_bucket_name`) | `apps/predict·call-api·simulator·weather-cron/deployment.yaml` 4곳 | `NoSuchBucket` |

바뀌지 않아 손댈 필요 없는 것(재확인): IRSA 역할 ARN 9곳, SQS 큐 URL 3곳, ECR 주소, EKS 클러스터 이름, EC2NodeClass 셀렉터, 네임스페이스·ServiceAccount·ScaledObject 이름.

### 8-2. 재구축 순서 뼈대
```
1) infra: alb_dns_name=""로 리셋 → 첫 apply(로컬·사람이 직접 — CI가 먼저 하면 사람이 kubectl 못 씀)
2) infra: output 4종을 배포팀에 전달, kubeconfig 재발급
3) 배포팀: ArgoCD 설치(명령은 `make install-argocd`로 있음, 담당자 미정 — teardown_체크리스트.md §6 게이트④)
4) 배포팀: 위 8-1 10줄 반영 + PR + 머지 → Application 전부 Synced/Healthy 확인
5) 앱팀: 이미지 6종 재빌드(dev push 아니라 workflow_dispatch로 — push면 바뀐 서비스만 빌드돼 나머지가 ImagePullBackOff)
6) 인프라: IAM 콘솔 수동 정책의 버킷 접미사 교체 (앱팀 모델 업로드보다 먼저)
7) 앱팀: model.pkl·metadata.json 재업로드
8) 배포팀: Ingress 올림 → 인프라: alb_dns_name에 새 ALB 주소 넣어 2차 apply(CloudFront 생성)
9) 인프라: CUR 버킷 이관 + 정의 재생성 (8-4 참고. 급하지 않음 — 위 단계들과 순서 안 겹침)
10) 완료 확인: 노드 Ready·파드 Running·Application 전부 Healthy·plan No changes·서비스 URL 200
```

### 8-3. `hailcast-rds-secret` — #58 머지로 절차가 바뀜 (조용빈님 지적 반영)

기존 런북(2026-07-28 오전 기준) 서술:
> "자동으로 안 생긴다. 반드시 둘 다 해야 한다 — ① ESO CRD 설치, ② `kubectl create secret`으로 수동 생성"

변경된 사실(같은 날 오후 #58 머지 — `feature/rds-secret-placeholder`):
- `manifests platform/external-secrets/secret-rds-placeholder.yaml`이 sync-wave `-1`로 들어와, ExternalSecret(기본 wave 0)보다 먼저 빈 Secret을 자동 생성한다.
- ExternalSecret 2개(`creationPolicy: Merge`)가 그 빈 Secret에 `DB_USER`·`DB_PASSWORD`·`DB_HOST` 키를 자동으로 채워 넣는다.

그래서 절차가 이렇게 바뀐다:

| 단계 | 기존(오전) | 갱신(#58 반영) |
| --- | --- | --- |
| ① ESO CRD 설치 | 필요 | 여전히 필요(자동 경로에서도 CRD 없으면 ExternalSecret 리소스 자체가 안 만들어짐). 주소 확정(2026-08-13): manifests `argocd/applications/external-secrets-app.yaml`의 `targetRevision`(현재 2.5.0)과 같은 태그의 CRD 번들. 적용 전 이 값이 그대로인지 재대조.<br>`kubectl apply --server-side -f https://raw.githubusercontent.com/external-secrets/external-secrets/v2.5.0/deploy/crds/bundle.yaml` |
| ② 수동 `kubectl create secret` | 필요 | 원칙적으로 불필요할 가능성 높음 — 다만 실제로 자동 채워지는지는 미검증(이 자동 경로가 빈 클러스터에서 검증된 적이 없고, 8/3 재구축이 첫 실행) |

8/3 리허설에서 반드시 확인:
```bash
kubectl -n argocd get application platform-secrets            # Synced인지 먼저
kubectl -n hailcast get secret hailcast-rds-secret -o jsonpath='{.data}' | jq 'keys'
# 기대값: ["DB_HOST","DB_PASSWORD","DB_USER"]  ← 이 셋이 다 나오면 수동 생성 생략
kubectl -n hailcast get externalsecret                         # rds-credentials·rds-endpoint 둘 다 SecretSynced
```
키가 비어 있거나 SecretSynced가 아닐 때만 아래 수동 patch를 백업으로 실행(infra `docs/비용관리.md`의 "재구축 시 hailcast-rds-secret" 절 참조, `create`가 아니라 `patch`인 이유는 빈 Secret이 이미 있기 때문):
```bash
RDS_SECRET="$(terraform -chdir=envs/dev output -raw rds_master_secret_arn)"
CRED="$(aws secretsmanager get-secret-value --secret-id "$RDS_SECRET" --query SecretString --output text)"
kubectl -n hailcast create secret generic hailcast-rds-secret \
  --from-literal=DB_HOST="$(aws ssm get-parameter --name /hailcast/dev/rds/endpoint --query Parameter.Value --output text)" \
  --from-literal=DB_USER="$(echo "$CRED" | jq -r .username)" \
  --from-literal=DB_PASSWORD="$(echo "$CRED" | jq -r .password)" \
  --dry-run=client -o yaml | kubectl apply -f -
```

조용빈님 말대로 자동 생성이 실패해도 수동 백업 절차가 그대로 유효해서 파드가 못 뜨는 상황 자체는 안 생긴다. 문제는 이제 불필요할 수도 있는 수동 명령을 팀원이 기계적으로 실행하는 비효율과, 런북이 최신 상태를 못 따라가는 패턴이 반복된 것이다. 이 문서를 갱신할 때마다 재검증한다.

### 8-4. CUR 버킷 이관과 정의 재생성 (2026-08-13 신설)

destroy 게이트①에서 살림(keep)을 골랐다. `terraform state rm`은 버킷을 state에서만 제외하는 것이라 실제 버킷은 그대로 남아있다. `modules/storage/cur.tf`가 `random_id.cur_suffix`·`aws_s3_bucket.cur`를 조건 없이 선언하고 있어서, 다음 apply는 이 버킷을 state에서 찾지 못해 새 버킷을 하나 더 만든다. 그래서 옛 버킷 내용을 새 버킷으로 옮기고 옛 것을 지우는 절차가 필요하다.

처리 방식 확정 — (c)안. 새 버킷 생성을 허용하고 아래 절차로 마이그레이션한다(2026-08-13 확정).
(a) `terraform import`로 옛 버킷을 state에 복귀 — 근본 해결이나 `random_id` 임포트가 까다로워 기각.
(b) 코드에 조건부 플래그를 추가해 기존 버킷을 data source로만 참조 — 검증 안 된 코드를 넣는 것이라 기각.

확인 필요(2026-08-13): CUR 소급 여부 실험을 위해 8/13에 CLI로 `hailcast-dev-cur` 리포트 정의를 옛 버킷 대상으로 이미 만들어 놓았다. 아래 순서(새 버킷 생성 후 정의 재생성)를 그대로 따르면 같은 리포트 이름이 이미 존재해 `DuplicateReportNameException`이 날 수 있다. 진행 전에 `aws cur delete-report-definition --report-name hailcast-dev-cur --region us-east-1`로 기존 정의를 지운다.

순서(위 충돌 해결 후 적용):

```bash
# 1) 옛 버킷 파일을 새 버킷으로 복사 — 정의 재생성보다 먼저(안 그러면 AWS가 새로 쓰는
#    cost_and_usage_data_status·crawler-cfn.yml을 옛 파일이 나중에 덮어씀)
OLD_BUCKET=<옛 버킷 이름 — aws s3api list-buckets로 hailcast-dev-cur 접두어 조회>
CUR_BUCKET=$(terraform -chdir=envs/dev output -raw cur_bucket_name)
aws s3 sync "s3://$OLD_BUCKET/" "s3://$CUR_BUCKET/"
# 확인: 두 버킷 객체 수가 같아야 한다
aws s3 ls "s3://$OLD_BUCKET/" --recursive | wc -l
aws s3 ls "s3://$CUR_BUCKET/" --recursive | wc -l

# 2) 새 버킷 이름으로 CUR 정의 재생성 — 첫 배달까지 최대 24시간
aws cur put-report-definition --region us-east-1 --report-definition "{
  \"ReportName\": \"hailcast-dev-cur\", \"TimeUnit\": \"HOURLY\",
  \"Format\": \"Parquet\", \"Compression\": \"Parquet\",
  \"AdditionalSchemaElements\": [\"RESOURCES\"], \"S3Bucket\": \"$CUR_BUCKET\",
  \"S3Prefix\": \"cur\", \"S3Region\": \"ap-northeast-2\",
  \"AdditionalArtifacts\": [\"ATHENA\"], \"RefreshClosedReports\": true,
  \"ReportVersioning\": \"OVERWRITE_REPORT\"
}"

# 3) 객체 수 일치 확인 후 옛 버킷 삭제 — 안 지우면 다음 teardown의 CUR 가드가
#    버킷 이름 두 개를 받아 조용히 건너뛰어진다(teardown_체크리스트.md 10-1절 3중 가드 참고)
aws s3 rm "s3://$OLD_BUCKET/" --recursive
aws s3api delete-bucket --bucket "$OLD_BUCKET" --region ap-northeast-2
```

4) 규약서 5-9절의 CUR 버킷 이름(대상 버킷·CLI 예시의 `S3Bucket` 값)을 새 이름으로 갱신.

## 9. 확인 안 된 것 (재구축 쪽)

번호 1·6·7은 destroy 쪽이라 `teardown_체크리스트.md` §9에 있다. 아래는 재구축 쪽 2~5번이다.

| # | 항목 | 왜 모르나 |
| --- | --- | --- |
| 2 | `alb_dns_name`을 옛 값으로 둔 채 apply했을 때 Route53이 없어진 ELB DNS를 alias 대상으로 받아주는지 | 조회로 판별 불가(destroy 7-6·이 문서 8-2 순서로 이 경우 자체를 피하고 있음) |
| 3 | SQS 큐 삭제 직후 같은 이름으로 재생성 시 `QueueDeletedRecently`로 막히는지 | AWS 권장 대기 60초, 재구축을 바로 이어 하면 걸릴 가능성 |
| 4 | CUR 정의를 새 버킷 이름으로 재생성 시 콘솔이 버킷 정책을 덮는지 | 콘솔 경로 미시도 |
| 5 | 배포팀 계정에 `secretsmanager:GetSecretValue`·`ssm:GetParameter` 권한이 있는지 | 8-3 수동 백업 경로 실행 권한 미확인 — 거부되면 인프라 담당이 대신 실행 |

남은 결정 병목은 총 3개다. 성격이 둘로 갈린다.

"제3자가 이 문서만 보고 재구축" 가능 여부에 걸리는 병목 2개: ① ~~ArgoCD 설치 주체·명령~~ → 명령은 있음(ops `make install-argocd` → manifests `make install-argocd` → `scripts/install_argocd.sh`), 주체만 미정(8-2 3단계), ② 텔레그램 봇 토큰·채팅ID 보관처 — 값 자체가 인프라 문서 소관이 아니라 이 문서에 별도 절로 담지 않았다. 팀장 또는 모니터링 담당에게 요청한다. ~~ESO CRD 매니페스트 주소~~는 2026-08-13 해소(8-3절 — manifests targetRevision 대조로 직접 확인, 배포팀 답 불필요했음).

여기에 더해 성격이 다른 병목 1개가 있다. 8/13에 cur.tf 무조건 선언 문제가 새로 발견돼(8-4절) 다음 apply 자체가 막힐 수 있는 상태다. 이건 "제3자 재구축" 가능 여부와는 별개로 apply 전에 반드시 처리해야 하는 항목이다.

(원본 §9의 이 자리에 있던 "8/4 전 완성은 무리라는 게 이미선님 판단이고 팀장도 동의" 기록은 시점이 지나 뺐다. 결론(개선기간 과제로 이관)은 그대로 8/13 개선기간에서 진행 중이라는 뜻이다.)
